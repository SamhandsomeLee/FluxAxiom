# 架构设计检查清单

## 问题与边界
- 谁是功能使用者？可观察的成功/失败是什么？当前实际实现在哪里？
- 这是新能力、行为修复还是移交职责？哪些明确非目标？
- 改动是否跨 crate / trait / JSON schema / 公开兼容边界？需不需要 ADR？

## 状态与权限
- Run/Attempt/Event 的写入所有者是否仍为 RunHost？Engine 是否只通过 HostPort？
- 状态与事件是否应同事务？未知结果能否区分“失败”和“未确认”？
- Workspace 授权、敏感数据的日志和 blob 边界是否不变？
- Context 的 prepare/replay 是否确定性重建？策略是否能篡改保护集合？

## Rust 设计
- 借用还是拥有数据？生命周期是否跨 await？trait object 或泛型的取舍？
- Send/Sync/错误类型是否有实际需求？是否有不必要的 Arc/Mutex/clone？
- 依赖方向是否保持单向？新增抽象是否存在实际调用点？

## 验证
- 对应正常/异常/边界/并发/取消/崩溃/旧数据的测试是什么？
- 契约与 Serde 输出是否有完整断言？Replay/Trace 是否仍可核验？
- 哪些风险未测、哪些是建议而不是已完成事实？

最后交付决策记录（本次对话内即可），只有在用户授权后才写入 ADR 或代码。
