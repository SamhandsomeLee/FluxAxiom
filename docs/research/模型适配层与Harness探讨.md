# 模型适配层与 Harness 探讨

- 状态：讨论记录，不是决定。没有任何一条在这里被采纳为实现要求。
- 日期：2026-10-22
- 起因：A1.2 与 A2.1 阶段的多轮审查中，同一个编码模型（Grok，具体型号以使用者所述为准）反复出现「只改清单、不扫范围」的遗漏。由此讨论能否用 harness 补偿，并能否推广为按模型建立的适配层。
- 恢复条件：Agent 主体（P0a 的 Engine、Host、回放样本）搭建完毕之后再回到本文。

## 1. 证据范围

本文的观察只来自一个项目里的一次开发过程：

- 审查者看到的产出：`crates/run-host`、`crates/engine-custom` 的代码与文档改动。
- 被审查模型自己的事后反思（模型自述，未必准确反映当时的行为）。
- 审查者自己也是模型，有自己的盲区，且对 DeepSeek 的 `finish_reason` 取值、`tools: []` 的行为等未做核实。

样本很小，没有对照组。以下归纳是假设，不是结论。

## 2. 观察到的现象

被审查模型的行为模式：

1. **清单驱动，收口过早**：把审查意见当待办清单，点名条目改完即停，不再扫描同一批文件里的相邻问题。
2. **注意力窄而深**：对点名问题处理精细（如 `reasoning_content` 的三态建模、在 ADR 里标注官方未定义的行为），对同一页文档里的其他样例没有核对。
3. **对显式规则遵从度高**：注释格式、先写 ADR、错误分层执行一致；对没写成规则的隐含期望响应差。
4. **标注诚实，但只覆盖自己意识到的不确定**。
5. **局部正确，跨文件一致性需要外部检查**。

第二轮审查才发现的、第一轮没动的问题：工具的线上 JSON 格式、`token_count` 的 `unwrap_or(0)`、`derive(Debug)` 泄露推理原文、序列化失败被伪装成 HTTP 400。

## 3. 能否从架构或后训练报告推断模型特点

- **能推断得较准**：能力边界（上下文、模态、工具调用格式）、数据语言倾向、训练目标的大方向、接口约束。
- **推断很不准**：具体行为风格（收口倾向、扩展倾向）。它取决于后训练的奖励设计与数据细节，报告通常不披露。架构对行为风格的影响很弱，中间隔着训练。
- **报告的偏差**：厂商自选基准；很多失败模式不在基准里；模型会在同一名字下持续更新。
- **分档使用**：
  - 可信：接口、上下文、模态、定价、官方明确的限制。
  - 当作假设：报告强调的训练重点，用小评测验证。
  - 不可信：从架构直接推出的行为风格。

作者没有 Grok 内部架构的可靠信息，因此不把观察到的现象归因于具体架构。更可能的来源是后训练的奖励设计、推理预算与档位设置、以及 agent 脚手架。「Fast」「High」这类档位是否影响这类遗漏，是可检验的假设，尚未检验。

## 4. Harness 能解决什么

按可靠度从高到低：

1. 测试与 lint：失败就过不去，与模型无关。
2. hook：在提交或收尾时自动检查，模型不能选择不遵守。
3. 独立审查步骤：另起上下文，只拿 diff 和约束清单核对。
4. 提示规则（如 `.cursor/rules/`）：最弱，最便宜，适合引导，不保证。

规则文件适合解决**流程性遗漏**（不做全量核对、汇报不分层）。不适合解决**能力性缺口**（没想到要去看某处、深层的跨模块推理）。规则过多会降低遵从度并占用上下文，常驻规则应保持精简。

已落地：`.cursor/rules/review-sweep.mdc`，把「改完后对动过的文件做全量核对」写成六条流程。它仍属提示层，兜底靠完整 JSON 输出测试和 lint。

## 5. 现有相近产品

以下来自训练知识，可能滞后，未联网核实。

| 层次 | 代表 | 与「按模型优化」的距离 |
| --- | --- | --- |
| API 归一化与网关 | LiteLLM、OpenRouter、Portkey | 只做格式与能力，不管行为 |
| 推理引擎的模型适配 | vLLM、SGLang 的 tool parser、reasoning parser | 最接近的现成例子，但只到格式层 |
| Agent 框架 | LangGraph、OpenAI Agents SDK、Claude Agent SDK、Google ADK、Pydantic AI | 模型无关，基本不按模型调优 |
| 提示或程序优化 | DSPy | 最接近自动按模型调优，粒度是提示 |
| 评测与观测 | Inspect AI、Langfuse、Braintrust、LangSmith；SWE-bench、Terminal-Bench | 提供画像所需的数据，不自动产出补偿策略 |
| 编码 agent 产品内部 | Aider、Cline、Cursor | 已在做按模型调整（如 Aider 的按模型设置表），但私有、写死在产品里 |

**为什么没有「agent 层的 vLLM」**：vLLM 的优化保持语义不变，可以做成通用可插拔层；agent 层的优化会改变行为，效果依赖任务与模型版本，没有统一衡量标尺，模型更新快、策略易过期。

**仍然存在的空白**（尚未联网核实）：没有标准化的模型行为画像；没有按画像自动选择补偿策略的中间层；没有跨产品共享的失败模式库。

## 6. 按模型建立适配层的思路

按**失败模式**分层，不按**型号**分层：

```
通用层（所有模型共用）
  ├─ 测试 / lint / hook / 独立审查
  └─ 汇报格式、范围边界

模型适配层（按观察到的失败模式开关）
  ├─ 收口过早型 → 强制全量核对、清单外追加扫描
  ├─ 过度扩展型 → 范围限制、禁止顺手重构
  └─ 工具调用不稳型 → 格式校验与重试
```

做法上的约束：

1. 先建评测，再建 harness。没有基线就分不清改动有效还是运气。
2. 一次只改一个变量（规则、推理档位、模型分别测）。
3. 补偿策略写成配置，不写成代码里的 `if model == …`。
4. 补偿策略必须能关闭，用于对照；模型升级后重新回归。
5. 通用层占大头，避免对某个模型依赖过深。
6. 画像的内容来自自己的评测，报告只作为带来源与置信度的先验。

## 7. 哲学视角

这些是类比，有启发性，不是严格推导，也不替代评测。

| 视角 | 对应问题 | 设计启发 |
| --- | --- | --- |
| 框架问题（McCarthy、Dennett） | 行动之后哪些事物相关、需要重新检查，无法穷尽形式化。视野盲区是它的实例。 | harness 的职责是外置相关性框架，并让框架可审计。画像应记录模型默认把相关性框架划在哪。 |
| 有限理性与满足即停（Simon） | 收口过早是停止规则太宽松。 | 「完成」是需要定义的判据。清单完成与范围内无已知缺陷是两件事，可做成一等公民。 |
| 遵循规则问题（维特根斯坦、Kripke） | 规则无法自己决定自己的应用，「请仔细对一遍」没有判据。 | 解释了提示规则弱、机械检查强。规则文字引导，判据约束。 |
| 归纳问题（休谟） | 过去行为不保证未来，模型升级可能使画像失效。 | 画像是带有效期的假设。 |
| 可证伪性（波普尔） | 画像要能被一次反例推翻。 | 写成可检验陈述，而不是「它比较粗心」。每条画像带来源、证据、日期、可证伪条件。 |
| 同一性（忒修斯之船） | 别名指向的权重变了，还是同一个模型吗？ | 画像绑定版本，不绑定名字。与 ADR-020 分开记录别名与版本一致。 |
| 古德哈特定律 | 度量变成目标就失效。 | 评测集要有保留集并定期更新；补偿策略可关闭以做对照。 |
| 分权（孟德斯鸠、「任何人不应做自己案件的法官」） | 同一视角会重复同一个盲区。 | 执行与核对不共享上下文，最好也不共享模型。 |
| 实用主义（皮尔士、詹姆斯） | 概念的意义在于可观察后果。 | 画像不必解释模型为什么这样，只需可预测并改善结果。 |

## 8. 可收成的设计原则（候选，未采纳）

1. 外置相关性框架：harness 替模型划定「该看什么」，且可审计。
2. 显式定义「完成」：完成是判据，不是感觉。
3. 约束优先于劝告：能机械检查的不靠自觉。
4. 画像是假设：带来源、日期、版本、可证伪条件。
5. 绑定版本，不绑定名字。
6. 执行与核对分权。
7. 保留集与对照组，防止过拟合评测。

## 9. 与 P0 计划的衔接

- A4 的「样本可回放」与「模型版本作为评测维度」（执行方案 §4.7 第 341–342 行）是画像所需评测基线的雏形。
- ADR-020 把型号配置化，为画像留了位置。
- 画像与补偿层要建立在评测数据之上，数据要等 A4 之后才有。**当前优先级是把 Engine–Host 端口、Fake Provider 与回放做扎实，不提前设计这一层。**
